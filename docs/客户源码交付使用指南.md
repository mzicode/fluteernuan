# 客户源码交付使用指南

本文是客户收到源码包后的统一入口。源码包只包含源码、配置模板、部署脚本和文档，不包含生产凭据、签名文件、数据库数据或已编译发布包。

## 1. 交付物清单

客户应收到以下文件：

| 文件 | 用途 |
| --- | --- |
| `source-delivery-<时间戳>.zip` | 完整源码压缩包 |
| `source-delivery-<时间戳>.zip.sha256.txt` | 压缩包完整性校验 |
| 包内 `MANIFEST-SHA256.txt` | 每个交付文件的 SHA-256 清单 |
| 包内 `SOURCE_DELIVERY_README.md` | 本次快照和安全边界说明 |

交付方应单独提供客户专属的域名、密钥、第三方账号和部署参数。不要把这些内容写回源码包或提交到公共代码仓库。

## 2. 客户阅读顺序

1. `README.md`：了解目录、技术栈和快速启动方式。
2. `SOURCE_DELIVERY.md`：确认交付边界和排除项。
3. `docs/源码目录说明.md`：了解客户端、后端、管理后台、脚本和文档目录。
4. `docs/产品功能清单-前后台.md`：核对本次源码覆盖的功能域及启用条件。
5. `docs/ARCHITECTURE.md`：理解客户端、API、数据库和对象存储关系。
6. `docs/CONFIGURATION.md`：准备生产环境变量和密钥。
7. `docs/OPERATIONS.md`：执行启动、迁移、备份、发布和回滚。
8. `docs/API接口完整参考.md`：查看自动生成的 HTTP 方法、路径、鉴权层级和源码注册位置。
9. `docs/接口与数据流说明.md`：查看业务数据流、客户端调用边界和补充说明。
10. `docs/客户源码交付一键部署手册.html`：离线查看端口域名矩阵、各端打包、接口、Docker 一键部署和运维资料。
11. `docs/客户域名替换与Docker一键交付小白教程.md`：按小白步骤完成 DNS、宝塔、HTTPS、线上预编译 Docker 包和域名替换。
12. `docs/源码使用与合规责任协议.md`：部署前由客户和管理员阅读并确认合法合规使用责任。
13. 本文第 3 至 8 节：按客户环境部署、验收和交付。

## 3. 目录与责任边界

| 目录 | 内容 | 客户交接时需要做的事 |
| --- | --- | --- |
| `backend/` | Go API、迁移、任务和 WebSocket | 配置数据库、Redis、对象存储、JWT 和第三方服务 |
| `lib/`、`android/`、`ios/`、`windows/`、`macos/`、`web/` | Flutter 多端客户端 | 配置客户端接口地址、应用签名和平台能力 |
| `admin/` | 运营管理后台 | 设置 API 地址并构建静态资源 |
| `admin-kf/` | 客服管理后台 | 设置 API 地址并构建静态资源 |
| `h5/` | 独立 H5/PWA 客户端 | 设置 `VITE_API_BASE_URL` 和媒体地址 |
| `official-site/` | 通用帮助、支持和隐私静态页面 | 发布到客户自己的静态站点或合并到客户官网 |
| `compose.yaml`、`docker/` | 本地和容器部署 | 复制配置模板，替换全部密码和域名 |
| `scripts/` | 构建、验收、打包和运维脚本 | 先阅读脚本参数，再在隔离环境执行 |
| `docs/` | 架构、配置、接口、部署、测试和安全资料 | 作为实施和验收依据 |

说明：当前工作区未发现 `h5/` 目录，因此本次快照不包含独立 H5 源码；`web/` Flutter Web 客户端仍随包交付。若客户合同包含独立 H5，应在打包前补入该目录并重新生成清单和 SHA-256。

## 4. 最小本地环境

建议使用一台 Linux 或 macOS/Windows Docker 主机，安装：

- Docker Engine 或 Docker Desktop，以及 Docker Compose v2。
- Go 1.24，用于后端编译和单元测试。
- Flutter/Dart，与 `pubspec.yaml` 约束的版本一致。
- Node.js 和 pnpm，用于 `admin/`、`admin-kf/`、`h5/`。
- FFmpeg/ffprobe；启用媒体处理时必须安装。

启动隔离本地环境：

```bash
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:8080/health
```

默认开发端口：API `8080`、运营后台 `8082`、MySQL `3306`、MongoDB `27017`、Redis `6379`。验收环境必须使用独立端口、数据库和 Redis DB，不得连接客户生产实例。

## 5. 配置与部署

### 后端

复制配置模板后至少设置：

```text
CUSTOMER_IM_SERVER_MODE=release
CUSTOMER_IM_SERVER_BASE_URL=https://api.<customer-domain>
CUSTOMER_IM_ALLOWED_ORIGINS=https://app.<customer-domain>,https://admin.<customer-domain>
CUSTOMER_IM_WS_ALLOWED_ORIGINS=https://app.<customer-domain>
CUSTOMER_IM_JWT_SECRET=<customer-generated-secret>
CUSTOMER_IM_SETTINGS_ENCRYPTION_KEY=<customer-generated-secret>
CUSTOMER_IM_MYSQL_*
CUSTOMER_IM_MONGODB_*
CUSTOMER_IM_REDIS_*
```

生产环境禁止使用 `compose.yaml` 中的开发密码和 JWT 密钥。生产模式必须配置明确的 HTTPS Origin，不能使用 `*`。

### 管理后台和 H5

分别在 `admin/`、`admin-kf/`、`h5/` 安装依赖并构建：

```bash
pnpm install --frozen-lockfile
pnpm build
```

构建前把 API 地址替换为客户地址。静态资源应部署在客户自己的域名下，并通过反向代理转发 `/api/v1` 和 WebSocket。

### Flutter 客户端

使用客户自己的签名、Bundle ID、应用商店账号和推送配置。接口地址通过 Dart Define 或客户配置注入，不要把生产密钥写入源码：

```bash
flutter pub get
flutter build apk --release
flutter build web --release
flutter build windows --release
```

Android、iOS、Windows、macOS 必须分别记录构建结果；一个平台构建成功不代表其他平台可发布。

## 6. API 与 WebSocket 参考

完整接口目录以 `docs/API接口完整参考.md` 为准。该文件由
`scripts/generate-api-reference.py` 从后端路由注册生成，包含当前主服务的
HTTP 方法、路径、鉴权分层、处理器线索和源码行号；路由改动后执行：

```bash
python3 scripts/generate-api-reference.py
python3 scripts/generate-api-reference.py --check
```

`docs/bot-api-p1.openapi.yaml` 是 Bot 机器接口的独立 OpenAPI 文档，不能代替
主服务接口目录。请求字段和响应模型以路由对应的 Go handler、Flutter/Vue
客户端模型及接口测试为最终依据；交付时应把生成文档和源码一起冻结，不能只
交付一份手工摘录。

API 根路径为：

```text
https://api.<customer-domain>/api/v1
```

WebSocket 地址为：

```text
wss://api.<customer-domain>/api/v1/ws
```

主要 API 分组（完整路径见上面的自动生成文档）：

| 分组 | 能力 |
| --- | --- |
| `/auth` | 注册、登录、刷新 Token、退出、找回密码、二维码登录 |
| `/user` | 当前用户、资料、设备、隐私、推送、黑名单 |
| `/chat` | 会话、群组、频道、成员、公告、置顶和搜索 |
| `/message` | 发送、列表、同步、撤回、编辑、转发、已读和媒体 |
| `/contact` | 联系人、好友请求、备注和黑名单 |
| `/moment` | 动态、评论、点赞、话题和搜索 |
| `/call`、`/meeting` | 音视频通话和会议 |
| `/upload` | 图片、视频、语音、头像和文件 |
| `/wallet` | 钱包、订单、充值、提现、红包和转账 |
| `/admin`、`/service-admin` | 运营后台和客服后台 |
| `/app` | 客户端设置、公告、协议和热更新 |

统一响应结构、分页约定、错误码、上传分片流程和 WebSocket 事件表见
`docs/API接口完整参考.md`。HTTP 2xx 或 `code = 0` 只能证明接口层返回，不能替代最终业务验收。

## 7. 发布前验收

### 自动检查

```powershell
pwsh -File scripts/verify-source-delivery.ps1 -Root <staging-directory>
pwsh -File scripts/check-delivery-identity.ps1 -Root <staging-directory> -StrictBranding
```

### 功能验收

- API 健康检查、登录、刷新 Token、退出。
- WebSocket 连接、消息发送、接收、补拉和重连。
- 图片/文件上传与鉴权下载。
- 管理后台登录、用户管理和基础设置。
- 客服后台登录、会话查看和权限边界。
- 数据库迁移、备份和恢复演练。
- Android/iOS 或其他目标平台的真实设备安装和核心流程。

跨用户或跨设备的消息、通话、推送和机器人功能，至少使用两台真实设备验证最终可见结果，并记录 App ID、版本、运行时 REST/WS 地址、后端版本、数据库迁移状态和功能开关。

## 8. 交付建议

推荐采用“源码包 + 私密参数 + 验收记录”三件套：

1. 源码包只通过固定打包脚本生成，并附 ZIP SHA-256 和包内文件清单。
2. 客户专属域名、数据库口令、JWT 密钥、对象存储、支付、短信、推送和签名材料通过独立加密渠道提供。
3. 交付双方共同记录源码快照、工具版本、部署环境、迁移版本、构建产物 SHA-256 和验收结果。
4. 约定源码支持范围、缺陷修复期限、第三方服务费用、客户自行改动后的责任边界和凭据轮换责任。

源码包不应直接承诺“上线可用”。只有目标后端和客户端部署完成，并完成目标环境的真实设备冒烟测试后，才能报告线上通过。
